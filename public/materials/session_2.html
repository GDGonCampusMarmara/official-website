Architecture of Tomorrow · Session 2

What's Shaping Software Now?
AI Agents, Platform Engineering & the Near Future

This session is about learning how to read the direction of software without treating every new term like a commandment.

Software is being reorganized around loops, context, internal platforms, agent orchestration, and stronger control over where decisions actually run. The point is not to memorize a trend list. The point is to recognize which shifts are structural, which are temporary, and which are worth building around.

01

Why this conversation matters right now

Some changes are cosmetic. Some change how software gets built, run, and governed. The current wave around agents and platforms matters because it changes both system design and engineering culture at the same time.

Working claim

The next few years are less about choosing a favorite stack and more about deciding what kind of engineering culture can survive agents, distributed systems, and faster product cycles.

That is why agents, context protocols, internal platforms, and well-architected simplification are showing up in the same conversation. They all deal with the same pressure: more moving parts, less patience for friction, and a much higher cost for weak boundaries or missing guardrails.

What feels durable
  • Agent systems need governance, data architecture, and measurable control.
  • Agents are also becoming a delivery culture question: review, traceability, ownership, and recovery matter more now.
  • Platform engineering keeps growing because teams need paved roads, shared defaults, and a way to spread working practices.
  • Interoperability is becoming a real architectural concern because tools, context, and permissions now cross more boundaries.
02

AI agents: the useful mental model is the loop

This section borrows its backbone from your Mozilla Berlin talk: feedback systems before AI, the agent as a loop with memory, isolation and determinism, and the importance of where the loop closes. The extra claim here is that agents are also teaching teams a new set of development habits.

From your earlier deck

An agent is a loop with memory

The clean version is still the best one: input arrives, the system interprets it using memory and model context, decides the next action, acts, then folds the outcome back into the next iteration. This makes the agent easier to reason about than if we talk about it like a personality.

  • input
  • interpret
  • decide
  • act
  • update memory
Feedback systems

Feedback loops existed long before AI agents

A thermostat measures temperature, compares it to a target, then adjusts. CI/CD deploys, observes, and rolls back when needed. Autocorrect watches what you type, compares it to patterns, then suggests a correction. Agents belong to the same family: they observe, decide, act, and check the result again. The new part is that one step in that loop is now probabilistic instead of fully hand-written.

Why this matters

An agent is not just an LLM call

The LLM helps interpret and propose the next move. The agent decides how to use that output inside a goal, a set of tools, and a control loop. Then the correction layer checks whether the step was safe, useful, and worth continuing. That is why validation, guardrails, tool boundaries, and replayable traces matter so much in agent systems.

03

The anatomy of an agent

Once the loop idea is clear, the next step is to make each part concrete. This is where the architecture gets real: what the LLM does, what the agent owns, and where the control and correction loop has to step in. It is also where teams start discovering the new rules their engineering culture has to absorb.

Striking sentence

The LLM predicts. The agent organizes. The control loop decides whether the system should trust, correct, continue, or stop.

That framing keeps the discussion technical. It also lines up with the strongest parts of the 12-factor-agents guide: own your prompts and context, keep tools structured, keep execution state close to business state, own your control flow, and make it easy to pause, resume, observe, and recover. Use the principles as design pressure, not as a badge collection.

Merged view

LLM + agent + control and correction loop

This is the practical shape you can explain on a whiteboard and still defend in production. A request enters the system, the LLM helps interpret the situation, the agent chooses the next step, a tool or action gets executed, and then a control layer checks what happened before the next turn continues. In short: gather feedback, analyze it, act on it, then repeat with better context.

  • LLM: interprets intent, summarizes context, proposes next actions
  • Agent: holds the goal, chooses tools, tracks state, sequences steps
  • Control and correction loop: validates, scores, retries, asks for approval, or stops
  • memory and execution state keep the loop from starting from zero every turn
  • evaluation and handoff decide whether the result is good enough to keep
LLM layer

Interpret the situation and propose the next move

This is the part that reads the prompt, absorbs context, and predicts the next reasonable step. Good teams do not treat prompts as throwaway strings. They version them, test them, and deliberately shape the context window using retrieval, model routing, and structured context exposure. The model can only reason over what actually reaches it.

Agent layer

Choose tools, hold state, and move the work forward

The agent is the part that turns prediction into procedure. It decides which tool to call, what step comes next, what should be remembered, and when a task is done. This is where typed tools, JSON Schema, OpenAPI-shaped interfaces, Pydantic or Zod validators, workflow state, and MCP servers start to matter.

Control + correction

Check the result before the loop continues

This is the part many demos skip. Validation, retries, approvals, rollback, and stop conditions belong here. Once an agent touches real work, pause and resume are not luxury features. Teams increasingly use state machines, checkpointers, event logs, evals, and human review to keep the loop safe and recoverable.

Concrete analogies

The same loop in simpler systems

  • Thermostat: measure, compare, adjust
  • CI/CD: deploy, observe, roll back
  • Autocorrect: read text, compare pattern, suggest fix

Agents feel new because one part of the loop is now language-driven and probabilistic, but the larger engineering shape is already familiar.

Established tools and patterns

What teams are already standardizing around

  • OpenTelemetry, Langfuse, or similar tracing and replay tools for understanding runs
  • schema validation, policy checks, and approval workflows before side effects
  • workflow engines and state machines when a loop needs durable checkpoints
  • retrieval, scoped memory, and MCP-style tool/context boundaries instead of stuffing everything into one prompt
  • event-driven coordination when multiple workers or agents react to new facts
04

Where the loop closes changes the system

One of the strongest ideas in your earlier presentation is that intelligence is not simply where the model is. It is where the loop closes. That changes privacy, cost, latency, portability, and control.

Loop placement

Local, edge, cloud

Local loops can improve privacy and latency. Edge loops can reduce round trips. Cloud loops still handle heavy compute and shared services. The architectural question is not which one is morally best. It is which one fits the system pressure.

  • local loop: private, close to user, constrained by device
  • edge loop: regional, lower latency, shared execution
  • cloud loop: heavy compute, coordination, central memory and tools
Six taxes of local loops
  • memory
  • distribution
  • variance across machines
  • energy
  • heat
  • context limits

Those are not reasons to avoid locality. They are the price of moving intelligence closer to the user.

Browser-native angle

The browser already exposes primitives that make it worth taking seriously as a runtime. The 3W idea makes that concrete: WebLLM for local inference, WebAssembly for portable agent logic, and WebWorkers for keeping execution isolated and responsive off the main thread. Add IndexedDB for longer-lived local state and normal Web APIs as tools, and the browser stops looking like a thin client and starts looking like a real execution surface.

05

Platform engineering: where good agent work becomes repeatable team practice

Agents and platforms belong in the same story. Once a team discovers what actually works with prompts, tools, evaluation, permissions, tracing, and deployment, that knowledge has to become repeatable. Otherwise the next team forgets the lesson, rebuilds the same mistakes, and calls it innovation. Platform engineering is what turns agent experiments into engineering culture.

Internal platforms

Catalogs, paved roads, and shared memory for the organization

A platform team is needed when local wins do not spread on their own. One team learns how to trace an agent loop, another learns safe tool boundaries, another learns how to keep deploys calm, and none of it compounds unless someone turns those lessons into defaults that other teams can actually reuse. That is not just tooling work. It is cultural memory turned into software.

  • software catalog so teams know what already exists and who owns it
  • golden paths for common tasks like service setup, tracing, evaluation, and deploy
  • shared policy, docs, ownership, and observability in one place
  • self-service templates so good practice travels faster than folklore
  • guardrails that stop anti-patterns from becoming normal team behavior
Why it matters

Without a platform approach, every strong technical decision stays local. The organization keeps paying for repeated setup work, scattered documentation, incompatible tooling, and deployment rituals that only a few people know how to survive. Broken culture usually looks like uncontrolled software units multiplying faster than teams can understand them.

Where it meets agents

If you build a great agent product but have no way to spread the winning patterns, tomorrow another team will re-learn prompt versioning, tool contracts, evaluations, tracing, and guardrails from scratch. Platform engineering is how agent lessons become cultural infrastructure, so success is repeatable instead of accidental.

Good question

Does this platform make the next team faster and safer, or does it just centralize complexity behind a more polished interface? The answer usually tells you whether you are building culture or bureaucracy.

The connection

Agents create new operational lessons very quickly: where to keep state, how to validate tool calls, how to trace loops, how to review outcomes, how to recover from bad actions. Platform engineering is what keeps those lessons from disappearing into one team's memory. Without that shared foundation, teams drift into fear, ceremony, and avoidable friction, and the culture starts training people to hide uncertainty instead of managing it.

06

The near future: not one trend, but a stack of pressures

The next phase looks less like one big winner and more like a set of pressures that will keep colliding: agent governance, context interoperability, simpler cloud choices, and the need to turn successful practices into something teams can reuse without copying each other badly.

Governance

Agents need policy, permissions, evaluation, and data architecture

Once an agent can act instead of merely suggest, governance becomes a systems problem. Who can it access? Which tools may it call? What gets logged? How do you review outcomes? How do you measure whether it is helping?

Interoperability

Context and tool protocols are becoming real architecture

Tool calling used to feel ad hoc. Now protocol design is becoming part of the conversation, because agents need standard ways to discover context, tools, and workflows without every team reinventing the same plumbing.

Near-future picture

What will probably matter more than hype

  • clear boundaries between prediction and deterministic control
  • measured use of managed services to keep complexity survivable
  • agent systems that are observable, auditable, and portable
  • developer platforms that capture what worked and make it reusable
  • protocols and interfaces that make tools and context reusable
07

What often looks advanced but quietly slows teams down

When teams lack clear paths, shared defaults, and good complexity management, they usually compensate in expensive ways. These are the patterns of drag that appear when learning does not turn into repeatable practice and when platform guardrails are missing, weak, or ignored.

A useful warning

If a team cannot preserve what worked, it will mistake repeated pain for normal engineering life. In agent-heavy systems, that pain compounds very quickly.

Techno-bureaucracy

Process pretending to be engineering

When diagrams, tickets, approvals, and extra layers multiply faster than product learning, the work starts serving paperwork instead of the problem. Good platform work should remove this, not decorate it, by making the safe path easier than the ceremonial one.

FOD

Fear of deploy

If shipping feels dangerous, teams stop learning from reality. A healthy platform usually shows up here first: safe deploy paths, rollback, traces, checks, and smaller changes that make release feel ordinary again. Fear of deploy is often a sign that culture has no trusted mechanism for controlled change.

Auth too early

Security detail before product shape

Authentication and authorization matter, but not every prototype needs enterprise-grade identity design in week one. Teams often hide uncertainty behind security work because it feels respectable. Clear platform defaults help you delay the heavy parts until the workflow is real, then add them without panic.

Missing complexity management

Complexity left unmanaged becomes culture

If naming, boundaries, ownership, and scope are fuzzy early, teams end up paying compound interest later. Platform thinking helps because it forces reusable boundaries, not just reusable code. Complexity management is one of the first guardrails an engineering culture has to formalize.

Problem spread

Too many problems at once

Teams often slow themselves down by chasing adjacent challenges before proving the main solution. Breadth feels productive. Focus wins more often. A strong platform approach protects focus by making the boring parts easy to reuse so attention can stay on the core problem.

Time management

Architecture without pacing becomes drift

Time is an architectural input. If no one protects decision windows, review cadence, and delivery rhythm, the system gets shaped by interruption instead of intent. Platform work matters here too because it shortens the path from decision to safe execution and gives teams fewer chances to drift into chaos.

Vibe-coding

Letting AI write code you no longer understand

If you can move fast with AI-generated code, great. But the first real bug will ask a harder question: can your team resume from where the model stopped? Healthy engineering culture answers that with traces, tests, reviewable diffs, ownership, runnable local setups, and enough operational history to debug what the agent helped create. Without those guardrails, speed turns into a maintenance trap.

08

What to watch without becoming trend-blind

Students do not need to chase every launch. They need a tighter filter. These questions are a stronger compass than any list of buzzwords.

Filter 1

What system pressure does this answer?

Latency, privacy, team friction, scale, governance, cost, or simply novelty.

Filter 2

What new complexity does it import?

Every helpful abstraction drags in a maintenance bill. Try to spot it early.

Filter 3

Who does this make stronger?

The end user, the product team, the platform team, or mostly the vendor story.

Filter 4

Will this still matter when the naming changes?

Good architectural ideas survive rebranding. Weak ones depend on slogans.

You do not need a perfect forecast. You need stronger judgment about which shifts are structural enough to build around and which ones are just temporarily loud.

Closing the session

The point of this session is not to turn students into trend reporters. It is to give them a better vocabulary for deciding where to look, what to build, and what to ignore.

What a strong ending sounds like

  • Agents are easier to reason about when treated as loops with memory.
  • Loop placement changes privacy, latency, cost, and control.
  • Platform engineering matters because team friction is an architectural problem.
  • The near future belongs to systems that balance autonomy with governance.
